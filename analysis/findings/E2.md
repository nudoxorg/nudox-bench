**VERDICT: NO FLOOR.** There is no similarity floor, minimum score, or cutoff
anywhere on the semantic path. The result set is sized by exactly three things:
a top-k `truncate` in `SemanticIndex::nearest`, a per-section `limit` fill in
`collect_semantic_hits`, and a final page cut in `do_unified_search`. The
`search` limit default is `50`, the cap is `500`.

## Unanswered
- Whether the exact-name row for `search_slice_with_raw` was *outranked* out of the 50-row page or never emitted by the name section at all (EVIDENCE §F, first bullet). C2.9 establishes the merge is a score-ordered union with no section priority, which makes "outranked" mechanically possible — a name hit on a private, non-top-level symbol is discounted by `visibility_weight` 0.4 (search/hits.rs:146) while semantic rows score `(cosine+1)/2 × 1.0 × 1.0`. Deciding between the two needs the actual scores of both rows for that query, which lives in a run, not in source. This is E1-fusion's question.
- Whether `SemanticIndex::nearest`'s brute-force scan has any upstream pre-filter (an ANN structure, a per-package shortlist) before it reaches this function. `guard.vectors` is populated in semantic.rs:1-440, which I read only via `rg`, and the answer would also touch `registry/vector/`, which is out of scope.

## Out of scope, noticed
- `search_symbols` (`do_search`) and `search` (`do_unified_search`) differ *only* in whether the semantic section is admitted (mcp/tools/mod.rs:313) — an adapter calling `search_symbols` gets the structural behaviour back with no other change.
- `SECTION_SEMANTIC`'s doc comment at search/mod.rs:103-106 still claims "empty in any build that installs no `Embedder`, which is every build in this repository today" — stale relative to the endpoint the A/B ran against.
- The `limit * 4` over-fetch in `collect_semantic_hits` exists so kind filters do not silently shorten the section (search/mod.rs:513-517); it is an over-fetch factor, not a floor, and is the one tunable constant on this path.
- `attach_addresses(page, &semantic_keys)` (mcp/tools/mod.rs:469) labels a hit as semantic-contributed from the pre-dedup semantic key set, so a row that hit in both sections is labelled semantic.
- `f32::EPSILON` in `cosine_to_relevance` is the closest thing in the codebase to a floor — a floor on the *value*, deliberately placed to prevent ties, never a filter on the *set*.
