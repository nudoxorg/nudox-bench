01

The question this instrument asks

For a real question about a real package — who calls this, what is this signature, what changed between these two versions — does a system produce the answer, how well resolved is the evidence, and what does it cost an agent's context?

The comparison set is deliberately unglamorous. Nudox is measured against the tools an agent already has on the machine — ripgrep and rust-analyzer — because those are what a code-intelligence index has to beat to be worth installing, and against four restricted versions of itself, to price each part of its own surface.

Read this before the numbers

  • Semantic search was off. Every Nudox response carried ~sem:unavailable(NoModelConfigured) — no embedding model was configured, so half of what search normally ranks with was disabled. These are structural-only numbers, and the run says so in-band.
  • Nudox held 3 of the 5 packages. The Go oracle binary is not installed, and the installed Python requests has no pyproject.toml for the producer to read. Those scenarios are recorded as declined, not failed.
  • The judge did not run. No OPENROUTER_API_KEY, so the two implementation scenarios are unscored and are held out of every pass rate rather than counted against anyone.
  • Ten scenarios is a small sample. Nothing here is statistically significant. This is a working instrument reporting its first readings, and the most useful findings in it are about the instrument.

03

How a number gets recorded

A run is a matrix: every adapter attempts every scenario, and each of the 70 cells in this run produced one recorded attempt. The pipeline below is the sequence a single cell goes through. It is genuinely a sequence — the output of each step is the input to the next, and every step writes down what it did.

01

A scenario is written by reading the package

Each scenario is a TOML file holding a question a developer would actually ask, plus the answer, derived by reading the source of the pinned version — never recalled from memory. Every file opens with a comment naming the file and lines the truth came from, so a disputed result is settled by looking, not by arguing.

# Ground truth derived by reading memchr-2.8.3 directly, not from memory:
#   rg -n 'search_slice_with_raw' src/
# The six call sites in src/memchr.rs are at lines 31, 63, 96, 129, 167, 205,
# inside memchr, memrchr, memchr2, memrchr2, memchr3 and memrchr3.
id     = "rust/memchr/callers-search-slice-with-raw"
family = "retrieval"
task   = "callers"

[target]  ecosystem = "crates.io", package = "memchr", version = "2.8.3"
[probe]   name / symbol / query — the subject in every spelling

[truth]
mode   = "symbol_set"
all_of = ["memchr::memchr", "memchr::memrchr", "memchr::memchr2",
           "memchr::memrchr2", "memchr::memchr3", "memchr::memrchr3"]

[budget]  max_tool_calls = 4, token_budget = 4000

A scenario also records what it is sensitive to. This one deliberately excludes the architecture-specific backends from both all_of and none_of, because each is cfg-gated to one target and whether it belongs in the answer is a defensible design choice. Scoring a tool on a judgement call makes the number mean less, not more.

02

Each adapter maps the question onto its own surface

The scenario names a task and a subject, never a tool call. Each adapter decides how to ask: ripgrep wants a literal and a set of flags, rust-analyzer wants a symbol plus a file position over LSP, Nudox wants an address and a tool route. This is why the comparison can include things that are not MCP servers at all.

If an adapter cannot express a question, it returns declined with a written reason rather than a wrong answer — rust-analyzer does not speak go, go:github.com/google/uuid is not loaded in this corpus. Both reason strings are quoted verbatim in the report.

03

The exact bytes on the wire are metered

Requests and responses are kept as the raw text that crossed the wire — no deserialization into typed structs first, because the payload is the measurement. Two costs are counted and never mixed:

resident — every tool description plus every argument-schema description, paid once per session before a question is asked. marginal — the requests and responses for this one question.

Both go through a real BPE tokenizer, reported under cl100k_base and o200k_base together; where one figure is needed, the larger of the two is used, so no compactness claim is flattered by tokenizer choice. There is deliberately no cheap estimator path: a count-alphanumeric-runs proxy scores a 64-hex key as 1 token instead of ~50 — a 50× error on the largest single item in a Nudox payload, which is exactly what this benchmark exists to measure.

04

The attempt is scored and written to disk

Scoring is mechanical (section 04). Each run writes a timestamped report.json — every attempt, every fact verdict, every cost, every decline reason — and a report.md beside it. Every figure and table on this page is derived from that JSON; the run id is run-2026-08-30-165221.

{ "scenario_id": "rust/memchr/callers-search-slice-with-raw",
  "adapter": "nudox-full",
  "score": { "strict_recall": 1.0, "loose_recall": 1.0,
             "distractors": 0, "any_of_satisfied": true, "passed": true,
             "facts": [ { "fact": "memchr::memchr", "tier": "strict" }, … ] },
  "attempt": { "tool_calls": 2, "elapsed_ms": …,
               "cost": { "requests": {…}, "responses": {"cl100k": 1602, …} } } }
04

How an answer is scored

Almost nothing here is judged by a model. Who calls search_slice_with_raw has an answer you can read out of the source, and once it is written down, an attempt can be scored by matching text. That single choice is what makes the benchmark reproducible, free to re-run, and safe to put in CI.

Two recalls, not one

The subtle way a retrieval benchmark goes wrong is in deciding that a symbol "appeared". memchr3_iter can show up as a qualified path, as a Nudox address, or as a bare identifier in a line of source that grep happened to print. Those are not the same evidence, and collapsing them flatters whichever tool returns the most undifferentiated text. So every fact is matched twice:

strict — the fully-qualified path, with ::, . and / normalized to one separator so a single spelling matches Rust, Go and Python renderings. loose — the final identifier, on a word boundary, anywhere in the returned text.

The gap between them is the measurement. Word boundaries are load-bearing: memchr must not be credited by a line containing only memchr3, and there is a test pinning exactly that case.

Distractors, and the pass rule

A retrieval tool can score perfect recall by returning the whole package. So a scenario also names none_of: symbols a correct, narrow answer would not contain — near-misses and classic text-search false positives. Any one of them sinks the scenario.

A pass therefore requires all three at once: full strict recall, the any_of gate satisfied, and zero distractors. Deliberately strict — a partial answer to "who calls this" is a wrong answer to "who calls this".

This is not hypothetical — but the mechanism is not the one this repo's docs claim. On go/uuid/callers-parse, ripgrep reached 100% strict recall and still failed, because ParseBytes appeared in the output. Auditing the stored payload for this page showed how it got there, and it was not the regex: ParseBytes( cannot match \bParse\s*\(. All five of its mentions are context lines from uuid_test.go, pulled in by the adapter's -B 12 window.

So was the recall. MustParse and Scan were both credited from context lines carrying the enclosing func declaration — not from a matched call site. 78% of the 343 returned lines come from _test.go files, which is also where the 10,719-token cost went.

What this scenario measures, then, is the baseline's invocation: twelve lines of leading context and no test-file exclusion produced both the recall and the failure, and rg --glob '!*_test.go' would plausibly have passed it. The distractor rule did its job — a near-miss symbol did leak into an answer that should have been narrow — but this is a finding about the harness's ripgrep adapter, not a demonstration that text search cannot tell callers from callees.

The three verdicts that are not "wrong"

verdictwhat it meanshow it is treated
declined The adapter cannot express this question at all, and says why in writing. Never enters a pass rate. "Cannot ask" and "got it wrong" are different findings.
unscored An implementation scenario that needs the model judge, run with no judge available. Held out of the pass rate rather than counted as a failure.
degraded A system reported part of itself unavailable while answering — here, ~sem:unavailable(NoModelConfigured). Numbers still count, but the report leads with a banner naming the degradation, on every run that has one.
Folding these into failures would report rust-analyzer as bad at Go rather than inapplicable to it — and would let a misconfigured run pass silently as a result about the system.

Where a judge is still used, and why it is someone else's judge

Only the implementation family reaches a model panel — "using package X, build Y", which has no single right answer. The protocol is three models voting independently on two booleans, complete and relevant, with a pass requiring 2-of-3 on both. The panel is a constant in the source, not a config knob, because a panel that drifts between runs makes the runs incomparable.

That protocol is inherited unchanged from context-bench, the documentation-retrieval benchmark this harness is meant to be readable against. Changing the judging rule and the system under test at the same time would make the two sets of numbers incomparable — which is the entire reason for keeping a rule you would otherwise want to improve. What is judged is the context, not an implementation: no code is generated or run.

05

Why these numbers are supportable

Every property below is a mechanism in the harness, not an intention. Each names where it is enforced, so the claim can be checked rather than taken.

The same run gives the same answer

No temperature, no panel drift, no model deprecation quietly invalidating last month's numbers. Eight of ten scenarios are scored by string matching against a recorded answer, so a re-run reproduces the table exactly — and the whole thing costs nothing to re-run, which is what makes it safe to put in CI.

enforced by deterministic scoring in src/truth.rs; the judge is reachable only from Family::Implementation

The ground truth is traceable to a line of source

Every scenario carries a comment naming the file and lines its answer was read out of, at a pinned version. A disagreement about a result is therefore settled by opening the package — a failing run is a finding, not an argument about whether the question was fair.

enforced by convention documented in docs/SCENARIOS.md, visible in every file under scenarios/

A scenario that cannot fail is rejected

nbench list validates every scenario and refuses ones with no expected facts, a symbol-scoped task with no symbol, a diff with no second version, or an implementation family whose truth is not judged. The most common way to write a worthless scenario is to write one nothing can fail; the loader will not load it.

enforced by the scenario loader; run cargo run --bin nbench -- list

Cost is measured, never estimated

Real BPE, two independent vocabularies reported together, and the larger of the two used whenever one number is needed. Agreement between two vocabularies is what makes a compactness claim defensible; the absence of a fast estimator path is deliberate, because a character-run proxy is wrong by 50× on exactly the payload item that matters most.

enforced by src/tokens.rs, with a test pinning the 64-hex-key case

Recall alone cannot buy a pass

Precision is scored explicitly through distractor sets, so a tool cannot win by returning more text. The one 100%-recall failure in this run shows the mechanism firing — though an audit of the payload traced that scenario's recall and its distractor to the same -B 12 context window, so it prices the baseline's invocation rather than text search as such.

enforced by truth.none_of per scenario; any hit sets passed = false

There is no headline score, on purpose

Four things are measured — found it, how well resolved, what it cost, could it answer at all — and they trade against each other. Any fixed weighting would encode an opinion about that trade-off into what is supposed to be evidence about it. The summary is a table; the reader does the weighing.

enforced by the report format itself — see docs/DESIGN.md § no-headline-number

Degradation is reported in-band, at the top

This run's own banner leads with ~sem:unavailable on all five Nudox configurations, and with the ablation that could not be exercised. A benchmark that hid a disabled subsystem would be publishing a result about a configuration while implying one about a system.

enforced by the degraded-capability banner in src/report.rs, emitted whenever any attempt carries a capability warning

An ablation that did not run says so

The address-versus-hash ablation reported ~ablation:not-exercised rather than silently emitting a row identical to the baseline. The finding is real — search renders addresses, so the 64-hex key never crossed the wire — and it is recorded as an unexercised condition rather than as evidence.

enforced by the ablation policy check in src/adapter/nudox.rs

What this method does not support. It cannot tell you whether a model can drive these surfaces unaided — every adapter here follows a fixed, scripted tool path, so what is measured is the surface, not an agent's use of it. It cannot support a statistical claim at n=10. It cannot speak to Nudox's semantic search, which was switched off. And its ripgrep numbers price one particular invocation, not the tool's ceiling: the flags and context window are the adapter's choice, and on at least one scenario they decided the verdict.

One measurement limit worth naming — since closed. The strict/loose split only bites where a fact has a qualified spelling. In the Go and Python scenarios the expected facts are bare identifiers (MustParse, Scan), so strict and loose recall coincide by construction — and a grep context window can then manufacture recall by printing the enclosing declaration near an unrelated match. The resolution-gap column cannot see that, and did not.

The harness now measures it directly, as a matched column: strict recall counting only facts on a line the adapter actually matched, rather than ones it printed in the window around a match. It is the same distinction as strict-versus-loose, drawn for provenance instead of spelling, and it is the only one available where a fact is a bare identifier. 06

What the run actually shows

  1. The cost argument is the strong one; the accuracy argument is not yet made. On the Rust scenarios both systems attempted, Nudox and ripgrep tie at 3 of 4, separated by 13× in tokens and a zero resolution gap. Same answers, a fraction of the context is supported. More correct answers is not.
  2. Nudox's one exclusive question, it got wrong — for a fixable reason. Cross-version diff is the scenario neither baseline can attempt. Nudox returned 50 changed declarations in 3,745 tokens, but ordered by path, so alloc internals filled the page and the four added HashMap methods fell past the cut. The tool worked; the ordering buried the answer, and the harness took only page one.
  3. Two of the three Nudox failures were the harness using the tool wrong. The overview scenario sent a prose query ("memchr public exports") to a search that matches names and kinds — with the embedder off it matched almost nothing and scored 13%. Querying the package name instead reached 60% with no change to Nudox at all. Worth stating plainly: a benchmark's first findings are usually about the benchmark.
  4. The second tool call earns its keep; the escape hatch does not. oneshot saves 41% of the tokens and loses a scenario. search-only is 4.3× cheaper than the full surface and still answers two — a defensible default for a tight budget, and an argument for making the first response denser.
  5. Retracted: everything this run said about the escape hatch. This page originally read "graph-first costs the same as full and answers less: the schema card is cheap at 134 tokens, but writing a correct query against it is not free". Reading the transcripts afterwards showed why: every graph call the benchmark had ever made failed, in every run, with Field Package received an invalid value for argument name: $package. The adapter sent its variables under variables where the tool names the field args, entered at a root the schema does not offer, and walked an edge (referencedBy) that does not exist. The ablation was measuring an error message, so it never tested the thing it was named after. Fixed and re-measured, graph-first answers 5 of 5 at strict 1.00 — see results/2026-08-31-graph-fixed/. The lesson is the harness's, again: a tool that returns an error and a tool that returns a poor answer look identical in a pass rate.
  6. ripgrep is a much stronger baseline than it is usually given credit for — and its numbers move with its flags. It passes 5 of 7 as invoked here. But the adapter builds one fixed regex and context window per task kind, and the payload audit showed those choices deciding a scenario outright: the same window that manufactured 100% recall on go/uuid/callers-parse also carried in the distractor that failed it. Anything replacing ripgrep has to win on cost, precision, or reach — not on "can it find things at all" — and the baseline's own flags need tuning before its column is a fair floor.
  7. Reach is where the gap is structural rather than incremental. rust-analyzer declined 5 of 10 — every non-Rust package and every cross-version question — and no amount of tuning changes that. It is the axis where an index has a defensible answer, and the axis this run measured least, because the Go and Python producers were unavailable.

What would make the next run decisive

Turn the embedder on, so half of search's ranking stops being unmeasured. Install the Go oracle and index a Python source checkout, because polyglot reach is the strongest structural argument and is currently untested. Grow to roughly 50 scenarios weighted toward disagreement — ties tell you nothing, and ten is enough to debug an instrument, not to conclude with. Paginate diff in the adapter, since a real agent that missed its answer on page one would ask for page two. Make the keys ablation real by reading the structured key field, so the address scheme's saving is priced rather than assumed. Add an agent-driven mode, because a scripted tool path cannot answer whether a model can drive this surface unaided. Only then add the MCP field — Context7 and its neighbours — or the result will be a story about a misconfigured harness.

07

Reproducing it

The baselines need no endpoint, no API key and no network, and they are the floor every Nudox number is read against. doctor reports what is and is not set up and exits non-zero if a run would be degraded, so it works in CI.

# the part that needs nothing
cargo run --bin nbench -- doctor
cargo run --bin nbench -- run --config configs/baselines.toml

# with an endpoint (endpoint/ ships the standalone MCP server Nudox lacks)
./endpoint/target/release/nudox-endpoint --package "$HOME/.cargo/registry/src"/*/memchr-2.8.3
export NUDOX_MCP_URL=…  NUDOX_MCP_TOKEN=…
cargo run --bin nbench -- surface --per-tool
cargo run --bin nbench -- run --config configs/default.toml
cargo run --bin nbench -- run --config configs/ablations.toml
