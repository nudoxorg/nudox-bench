Zero Is Not a Score

A benchmark for code-intelligence tools, and what it reports when the tool under test cannot answer the question at all. Today it reports nothing about Nudox — deliberately, and that is the result worth publishing.

harness 9ca0328 Backend canonical c6fff26b3 scenarios 15 adapters 2 cells verified 182 / 182

Most benchmarks answer one question: which tool scored higher. This one spends most of its effort on a prior question — whether the number it is about to publish means what it appears to mean. Four days of that discipline produced a headline no marketing department would choose, and a measuring instrument you can check.

Why the first column is empty, not zero

0/0 is not a score of zero. Every scenario came back unsupported — the adapter could not ask the question at all — and the harness keeps that permanently separate from a wrong answer. Averaging the two would publish “Nudox 0%”, which would be both damning and false.

What the numbers say about the tool that can answer

ripgrep is here as a floor: the retrieval an agent already has without any index at all. Its pass rate is 75%. Its strict recall — did the required fact appear, fully qualified, anywhere in what came back — is 0.97. Those two numbers disagreeing is the whole point of splitting them.

The instrument's five rules

Each is a numbered entry in the repository's decision log, with the reasoning and — where it applies — the retraction attached.

D15

Unsupported is not failure

A tool that cannot express a question has told you something real about its reach, and something entirely different from answering wrongly. They occupy separate columns and are never merged. The canonical adapter was itself found guilty of breaking this rule — an unusable binary reached scoring and read as fail 0% — and was fixed to decline instead.

D7

Recall is split by provenance

Three recall numbers, not one. loose counts a fact found as a bare identifier anywhere in the reply; strict requires it fully qualified; matched counts only facts on a line the tool actually matched, rather than ones it printed in the window around a match.

D10

Predictions are written down before the run

Six predictions were committed to the repository ahead of the measurement that would test them. Four held. Two did not, and both are published with the reasoning that produced them. The falsified cost estimate is the useful one: it revealed that the dominant expense was never the thing being optimised — a single 21,276-token graph enumeration, not documentation text — which redirected the next round of work.

D17

A result that does not reproduce is not a result

Scoring is deterministic, so anyone can re-run these and get the same numbers. That sentence carries every other claim, so it is measured rather than asserted. A verdict that changes is an alarm — a published pass rate would then be partly luck. A cost that changes is ordinary for anything crossing a process boundary and is reported as a spread against its own floor.

Today's stronger test — reproduction across four days and 465 commits

The run above was not a repeat of a stored configuration. It used a freshly compiled harness, a freshly built CLI from a 465-commit-newer canonical, on a different day. Every verdict, every recall figure, the distractor count and the strict-versus-matched gap came back identical to 2026-09-03.

The only movement anywhere in the report was cost: one scenario at 37,744 → 37,190 tokens (−1.5%), moving the overall mean 8,780 → 8,740 (−0.46%). That is the spread the design predicts for cost and forbids for verdicts.

D11 · D22

Retractions are published, not quietly amended

The decision log carries its own failures. A patch that fixed a real ranking defect is marked INVALID because the crate it modified no longer exists — while the finding it rested on is kept, restated as a constraint on any future implementation. An audit that swept for unwrap and panic! and reported the code clean is marked SUPERSEDED: three of the four panics later found were bare slice expressions, which no such sweep could ever surface. The lesson recorded is not to audit harder but to match the shape of the search to the shape of the defect.

What was actually wrong, and got fixed

Six defects, each verified against the real code path before being touched rather than argued from reading:

DefectWhy it mattered
Three byte-offset cutsSize limits are byte counts applied to source text full of multi-byte characters. A cut splitting a character took down the whole run.
errored never displayedCounted from the beginning, rendered nowhere. A tool whose endpoint dropped looked identical to one answering wrongly.
Language-blind overview searchGrepping pub |export |public matches nothing in Python — scoring 0.00 for a question never actually asked.
Canonical adapter scored 0%An unusable binary reached scoring instead of declining.
A split judge panel passedA strict majority only for an odd panel, so one yes against one no passed — the single place this repo would have flattered a result.
A chatty judge crashed the runBrace positions located independently, so a reply whose last brace preceded its first inverted the slice and panicked.

Then the fixes were themselves measured. The pre-change harness was rebuilt and run against byte-identical scenario files, and all ten pre-existing cells came back identical on verdict, recall, distractors, cost and calls. That is the correct result — crash fixes and reporting columns are not supposed to move a score. The one number that did move belonged to the Python fix, and it made ripgrep look worse: 5,133 more tokens spent, same failure. What changed is that the number became true.

What would change this page

  • Binding a real RetrievalCapability and constructing the service with it. The benchmark adapter needs no change — it returns real attempts the moment index reports ready, and the ripgrep column above is a same-day baseline for that comparison to be read against.
  • A judge key, which moves the two implementation scenarios out of unscored and completes the family table.
  • A token with workflow scope, so continuous integration can gate on reproducibility rather than it being run by hand.
The instrument is finished before the thing it measures is. That is an uncomfortable place to publish from and the right order to build in — when the index is wired, the first number it produces will already be trustworthy.
