The harness works, reproduces exactly, and cannot currently measure Nudox at all — because on canonical the retrieval surface it was built to measure is not connected to anything.

Every retrieval action on canonical answers the same way:

Its own health roll-call agrees — index, graph and vector all report unavailable. This is not a setting. Three facts, each checked against 2f82d74b:

The index plane under server/index/* is real and carefully built — separate exact, lexical, qdrant and trustfall routes. It is simply not wired to the application service yet. No flag turns it on.

Look at strict recall against the pass rate. It sits at 0.97 overall and 1.00 in polyglot, while the pass rate is 70%. Every remaining failure is precision or cost, not finding. ripgrep answers “what does this package export” by printing the whole module — full recall, every distractor tripped — and answers a six-line question about memmem::find correctly for 38,051 tokens. That is the clearest demonstration in the repo of why recall alone is not a result.

Does any of this reproduce?verified

Every claim the benchmark makes rests on one sentence: the scoring is deterministic, so anyone can re-run these and get the same numbers. Until this week nothing measured that. A single report cannot tell a verdict that holds from one that alternates — it shows whichever value that run happened to land on.

configrunscellsreproduced
canonical (ripgrep + nudox-canonical)320100%
baselines (ripgrep + rust-analyzer)320100%

The middle row is the one worth having. rust-analyzer is a stateful LSP server, restarted and re-indexed for every run — precisely where a benchmark would be expected to wobble — and no verdict moved, with no cost drifting more than 5%.

Two kinds of movement are measured but never merged. A verdict that changes is an alarm: a published pass rate is then partly luck, and averaging does not repair it. A cost that changes is ordinary for anything crossing a process or a network, and is reported as a spread relative to its own floor. Recall that moves while the verdict holds counts as a failure to reproduce — the verdict survived on where the threshold happened to sit.

Defects found and fixed

All verified as real against the actual code path before being fixed, not argued from reading.

defectconsequence
Three byte-offset cutsEvery size limit is a byte count applied to source text, which is full of multi-byte characters. contains_word, the ripgrep adapter (twice in one expression) and mcp::truncate all panicked when a cut split a character — taking down a whole run.
errored never displayedCounted since the beginning, rendered nowhere. An adapter whose endpoint dropped looked identical to one answering wrongly — the exact conflation the unsupported and unscored columns exist to prevent.
Language-blind overview searchripgrep grepped pub |export |public for “what does this package export”. Python has no export keyword, so it matched nothing: 146 tokens, 0.00 recall — a zero for a question never actually asked.
Canonical adapter scored 0%A bug introduced with the adapter itself. An unusable binary reached scoring and read as fail 0% rather than declining.
View migration no-opDatabase views were rebuilt only when a column changed, so a changed view definition never propagated.

What the new column found in old data

Migrating the results database surfaced four outcomes that had been invisible: in run-2026-08-30-141350, rust-analyzer failed at LSP initialize on every memchr scenario and each was recorded as a scored failure. The tool never started, and the run reported that it answered wrongly.

That run is not one of the six under results/, so no published claim rests on it. Checked rather than assumed.

The ranking finding, carried forward

The earlier work on the deleted nudox-engine found a real defect: an exact name match on a pub(crate) symbol scored 1.0 × 0.6 = 0.60, a public semantic row scored (cos + 1) / 2, and the merge sorted on score alone — so any public symbol with cos > 0.2 outranked a literal name match. It could not win.

That patch is dead; the crate no longer exists. The finding is not, because the defect was never the weights — it was that two families’ scores were made comparable at all. It now sits in the greenfield plan as a law:

Results of different families are never ordered by a shared scalar. A query that touches more than one family declares a family precedence and orders within each family only.

The load-bearing half is the proof gate that came with it: a two-family test where precedence and score agree is satisfied by a comparator that ignores family. The legacy engine kept passing ranking tests the entire time it was broken.

What would change this page

  • Wiring the index plane to interface-core. The adapter needs no change — it returns real attempts the moment index reports ready, and the ripgrep column above is a same-day baseline for that comparison to be read against.
  • A token with workflow scope, so the CI definition can be pushed and verify can gate on reproducibility rather than being run by hand.
  • Confirming the SSH host key for the Backend remote, which changed and was accepted under instruction but is still unverified by a person.
